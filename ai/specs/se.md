# Searchable Encryption

## High-Level Overview

This SIP proposes the initial implementation of Searchable Encryption (SE) within DefraDB. 
The primary goal is to allow users to replicate their data to an untrusted remote node and still perform basic equality queries on specific encrypted fields without the remote node materializing plaintext. 
This phase focuses on establishing the foundational architecture, client-side tag computation, replication of index updates, and a dedicated query mechanism, using a deterministic tag/beacon approach for simplicity and to lay the groundwork for future, more advanced SE capabilities.

### Background & Context

DefraDB's local-first, peer-to-peer architecture, built upon MerkleCRDTs, empowers users with data ownership and offline capabilities. 
A common requirement is to have data replicated to an always-available remote node for backup and accessibility. 
However, if this remote node is untrusted (e.g., a third-party service), users are hesitant to store plaintext data or even fully decrypted data that the node could access.

Searchable Encryption aims to bridge this gap by enabling queries on encrypted data. The client encrypts data locally. 
For searchable fields, cryptographic metadata (an "encrypted index") is generated by the client and stored on the remote node. 
The client can then send a cryptographic token (derived from its query and SE key) to the remote node, which uses this token to search its encrypted index and return identifiers of matching documents. 
The client then fetches and decrypts the actual document blocks.

This initial phase will focus on the most basic and common query type: equality search. 
The approach will be similar to deterministic encryption or beacon-based systems in terms of the leakage profile for equality (i.e., it will leak equality patterns on the remote node), but the actual sensitive data will remain protected by DefraDB's standard randomized block encryption. 
This provides a balance between initial implementation simplicity and foundational security, with a clear path to incorporate more sophisticated SE schemes with stronger leakage protection in subsequent phases.

### High-Level Goal (Phase 1)

The goal of the first phase (or initial implementation) is to enable the simplest full cycle for searchable encryption which includes the following:
- Implement client-side generation of deterministic search tags for specific fields designated for searchable encryption.
- Establish a mechanism to replicate these search tag index updates from the client node to a designated remote/untrusted node via the active P2P replicator channel.
- Enable the remote node to store these search tags in its local Key-Value (KV) store, associated with the corresponding Document IDs.
- Provide a dedicated API for the client node to query this encrypted index on the remote node for equality matches, receiving a list of matching Document IDs as a result.
- Ensure the actual document data remains encrypted and is only decrypted by the client node after fetching.
- Lay an architectural foundation that is flexible enough to accommodate more complex SE schemes (range, FTS, stronger leakage profiles) in future phases.

### Proposed Design & Implementation (Phase 1)

#### Key Management 
Upon the initial startup of the node a new key will be generated 'searchable-encryption-key' (or something like) and store in the keyring. 
For this first phase, we will assume a single such SE key is used by a user for all their searchable encryption operations. 
Future iterations will utilize Orbis KMS and potentially more fancy key generation approach, like hybrid approach that derives a key from the client node's private key and the remote node's public key.

#### Schema Update
To enable searchable encryption on specific fields, developers will use a new GraphQL directive @encryptedIndex. 
In Phase 1, its usage will be straightforward: a developer can simply add @encryptedIndex to a field, or more explicitly `@encryptedIndex(type: "equality")`. 
This will signify that the field should be indexed for equality searches using default cryptographic settings, such as HMAC-SHA256 for tag computation with a standard truncation length for the resulting tag. 
This initial simplicity will allow us to extend the directive with more parameters for different query types (like range or FTS) and configurations in later phases.

#### Encrypted Index Metadata (Client-Side)
To manage Searchable Encryption (SE), each client node must locally maintain metadata for every encrypted index defined in its schemas via the `@encryptedIndex` directive. 
This is conceptually similar to the metadata already kept for standard `@index` secondary indexes.
This metadata is essential for processing document commits and generating SE queries. 
It needs to be stored persistently alongside the schema information.

For each defined encrypted index, the following core information must be tracked:
- A stable, unique Index ID (IndexID), analogous to secondary index IDs, used in the KV key path and tag computation's domain separator.
- The target Collection ID.
- The Target Field ID covered by the index.
- The Index Type (e.g., "equality" for Phase 1, potentially "range", "fts" later) which dictates the cryptographic operations.
- Any necessary Index Configuration specific to the IndexType (e.g., tag truncation length, potentially key references in the future).
- An optional, user-defined Index Name.

When processing commits, this metadata allows the client to identify relevant field changes, compute the correct old/new search tags using the associated configuration and the user's SE key, and queue the appropriate add/delete operations for the remote index via the replicator. When handling SE queries, the metadata provides the necessary IndexID, type, and configuration to generate the correct query tags and KV prefix for the RPC call to the remote node.

#### Encrypted Index Structure
The encrypted index itself will reside on the remote (untrusted) node, stored within its existing Key-Value store, which is currently BadgerDB. 
To keep SE data separate and organized, a dedicated root prefix, such as /se/, will be used. 
The KV key format is crucial for efficient lookups and proper namespacing. A proposed structure is: 
`/se/<Identity>/<CollectionID>/<IndexID>/<SearchTag>/<DocID>.`  

Let's break this down:
`<Identity>` client node's identity ensuring that data from different users (or nodes) on the same remote node remains distinct.
`<CollectionID>` is the internal unique ID of the collection.
`<IndexID>` is the internal unique ID of the encrypted index.
`<SearchTag>` is the deterministic cryptographic tag computed by the client (detailed next).
`<DocID>` is the unique document identifier.  

The KV value associated with this key can be minimal or even empty, as the DocID is already part of the key, making it efficient for lookups.

#### Search Tag
The search tag computation will occur on the client node. 
For Phase 1, we propose using HMAC-SHA256, with the output truncated to a standard length (e.g., 16 or 32 bytes) to balance uniqueness and storage. 
This is basically [how AWS does it](https://docs.aws.amazon.com/database-encryption-sdk/latest/devguide/searchable-encryption.html). 
The formula will be SearchTag = Truncate(HMAC-SHA256(UserSE_Key, DomainSeparator + PlaintextValue)). The UserSE_Key is the key mentioned earlier. 
The DomainSeparator will be a unique byte sequence created by combining the `<CollectionID>` and `<FieldID>` (e.g., `"<CollectionID>:<FieldID>"`) to prevent tag collisions for the same plaintext value across different fields or collections. 
PlaintextValue is the actual plaintext value of the field being indexed, taken from the relevant document commit.

#### Indexing logic
It will be triggered on the client node whenever a local commit is processed, before replication. 
The system will identify any fields in the commit marked with @encryptedIndex. 
It will then determine the previous and new states of these fields. 
For this phase, we will primarily focus on LWW (Last Write Wins) CRDTs, where the final value is straightforward to determine. 
Handling delta-based CRDTs will involve the client locally computing the full resulting state to generate the correct tag. 
If a field's value changes, the client will compute the OldSearchTag (for the previous value) and the NewSearchTag (for the current value). 
It will then generate the full KV keys for both and queue corresponding index update operations for the active P2P replicator.

To facilitate these updates, the active P2P replicator channel will be enhanced. We will define two new distinct P2P message types: 
1. `IndexAddOperation { bytes key_to_add; bytes value_to_add; }` (where value_to_add might be optional) and 
2. `IndexDeleteOperation { bytes key_to_delete; }`. 
After the standard block commits for a document update are successfully sent to a remote peer, any queued `IndexAddOperation` and `IndexDeleteOperation` messages will follow over the same direct P2P stream, ensuring index updates are applied after their corresponding data changes.

The remote node will handle these incoming index updates via its P2P service. 
Upon receiving an `IndexAddOperation`, it will add the record to the KV storage. 
An `IndexDeleteOperation` will trigger a delete operation. 

#### Querying Encrypted Index
We will introduce a dedicated API. For each schema type (e.g., User) that contains fields marked with `@encryptedIndex`, a new GraphQL mutation will be automatically generated. 
For instance, for a User type, a mutation like `encrypted_User(filter: EncryptedUserFilterInput!) { docIDs }` could be generated. 
The `EncryptedUserFilterInput` would be a dynamically generated input type allowing equality checks (`_eq`) only on fields marked with `@encryptedIndex(type: "equality")`.  
The client node will need a configuration (e.g., set at startup) specifying which remote peer hosts the encrypted indexes for its data. 
When the `encrypted_User` mutation is called, the client-side logic will use this configuration, retrieve the user's SE Key, compute the SearchTag from the filter value and then initiate a new P2P RPC call to the configured remote peer.  
The remote node, upon receiving this RPC, will perform a prefix scan on its KV storage. 
It will extract the `<DocID>` from each matching KV key, collect all unique DocIDs, and send this list back to the client in the RPC response.

#### Post-Query Document Fetch
In this initial phase it will be straightforward. The application will receive the list of docIDs from the `encrypted_User` mutation. 
It will then be the application's responsibility to issue standard DefraDB DQL queries (e.g., `User(docIDs: ["docID1", "docID2"])`) to retrieve the full documents. 
These subsequent queries can be directed to the same untrusted remote node (which holds the encrypted blocks) or any other peer. 
The client node's standard decryption logic will handle decrypting the fetched blocks.

## Future Work

- Delta CRDT Indexing: Implement reliable state reconstruction on the client before computing the Search Tag for delta-based updates. Ensure correct old/new tag handling.
- Index Compaction/Cleanup: Investigate if explicit cleanup of old index entries (beyond simple delete-on-update) is needed, especially if CRDT merges create orphaned index entries.
- Error Handling: Improve error handling in replication and querying (e.g., what if the remote node's index is corrupt or missing?).
- API Refinements: Add configuration options to `@encryptedIndex (e.g., beacon length)`.
- Key Rotation/Management: Introduce mechanisms in the keyring/API to rotate the SE key or use Orbis KMS. Update indexing logic to potentially handle multiple active keys or key versions.
- Range and FTS (Full Text Search) queries: Add support for range and FTS queries.
- Query Unification: Explore if/how the SE query API could be integrated more seamlessly into the main DQL/GraphQL interface (complex due to different return types and execution paths).
- Relationship Queries: Design and implement SE across document relationships (significant complexity).
- Batching: Batch index updates during replication. Batch KV operations on the remote node.
- Caching: Client-side caching of query results or intermediate data.
